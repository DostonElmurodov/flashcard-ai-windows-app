The manual `backup` mode checks the one running Compose API container and parses its configured database connection through the existing strict inventory helper. It probes only that database for server major version and database size using a read-only transaction. It checks local `pg_dump` and `pg_restore` versions, host free disk and available memory, then creates one custom-format archive through the verified API network namespace in `.owl-ai-private-backups` under the canonical deployment directory. Credentials and database target stay in libpq environment variables, outside command arguments and logs. The archive uses exclusive creation and remains `.incomplete` on failures. The private folder is mode 0700 and new files are mode 0600 on Linux. Completed archives are checked for nonempty size, SHA-256, and successful `pg_restore --list`; raw listing output is discarded. A private manifest records the archive reference and hash. The workflow logs only bounded status and resource metadata. This validates an archive; it does not prove a restore or the restored data.

Second-review changes: a per-deployment exclusive `flock` serializes backup runs through completion. Before launch, the helper checks available memory and enough free disk for a floor of the larger of database size or 256 MiB plus expected archive space. The namespace-side worker owns `pg_dump`, checks parent liveness and a 600-second deadline, and streams at most 64 KiB at a time while enforcing a two-times-database-size archive ceiling and the free-disk floor. It kills the dump process group and waits for the child on an ordinary boundary violation or timeout. The outer 620-second timeout is a fallback; if it fires, the helper reports that the worker failed to exit, and cleanup is not claimed. Concurrent unrelated disk growth may still consume free space between checks. The memory gate is a startup check, not continuous memory containment.

After the live memory-gate stop, the helper was changed to print five fixed numeric fields immediately before the resource gates: database size MiB, database server major, host free disk MiB, host available memory MiB, and host total memory MiB. It validates the numeric ranges and available-memory relationship to total memory first. Credentials, database name, deployment path, and query output remain absent from these lines. PostgreSQL client versions are checked later and therefore are not reported on a resource-gate rejection.

The measured 10 MiB database prompted a narrow memory-tier change: configured database size up to and including 64 MiB requires at least 256 MiB available memory at startup; a larger database still requires 512 MiB. The measured 400 MiB passes the small-database gate if it remains available on the next run. The lock, 64 KiB stream chunks, archive byte ceiling, disk floor, 600-second worker deadline, and read-only database access are unchanged. This startup threshold is not a guarantee of memory containment while dumping.
