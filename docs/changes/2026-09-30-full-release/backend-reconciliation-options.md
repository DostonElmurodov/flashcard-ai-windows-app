# Historical AI-usage reconciliation options — read-only analysis

Source reviewed: backend checkout `a6e2362c8e624338c564bfd88499cd1835c956c1`, 2026-09-30. No live database rows, provider invoices, or private purchase evidence were inspected. These are candidate release procedures, not authorization to change production records or quota policy.

## What the implementation actually does

- `AddStableOperationUsage.cs:184-204` accepts legacy `ai_usage.Date` values only as valid UTC `YYYY-MM-DD` or `YYYY-MM-DDTHH:mm` windows. It retains the original `ai_usage` rows. Lines 233-292 classify/import only nonnegative rows with a valid window and a defensible subject, and add their counts to durable `usage_buckets`; invalid or unproven rows become issues instead of zeroes.
- `AddStableOperationUsage.cs:272-279` adds `historical_paid_usage_unknown` for every pre-existing subscription, regardless of Apple environment or whether old usage rows exist. It also records `legacy_restore_usage_unknown` for every existing mobile grant and `deleted_account_root_unknown` for tombstoned claims. Lines 295-296 set the singleton `usage_accounting_state.Ready` to true only when the issue table is empty. A Production database containing a Sandbox/LocalTesting purchase is affected just the same.
- `OperationQuotaService.cs:16-28` first requires approved positive config and then refuses *all* AI when `Ready` is false; it does not check whether a historical issue belongs to the current caller. It picks the current UTC day and minute only **after** that gate (`:36-39`), and new reservations use the durable root (`:29-39`). A successful process start or `/health` therefore says nothing about AI readiness. No production reconciliation or readiness transition exists in this checkout; the only `Ready=true` updates outside migration occur in tests.
- The older `AccountAiUsageService.TryConsumeAsync` and `AiUsageService.TryConsumeAsync` can bypass old counters in Development test mode. The root's live read-only probe observed `test_mode: true` on the previously deployed server, but the exact past call history is unknown. Zero `ai_usage` rows would **not** prove zero provider calls or paid usage.
- `UsageSubjectResolver.cs:63-83,94-121,136-158` requires server-token owner proof before attributing an originating installation's free buckets to a purchase, and uses an attribution key to avoid repeating that transfer. A proved account claim rolls purchase counters into the account root. Historical UUID equality alone cannot authorize either transfer.

## Can the old counts expire naturally?

Yes, in the narrow sense of **quota comparisons**: a valid daily bucket from yesterday is never selected for a new UTC day, and an old minute bucket is never selected for a new minute. The historical rows and imported buckets remain stored. The issue rows and `Ready=false` have no TTL and do not change at midnight. Waiting without a reviewed reconciliation implementation keeps all AI blocked. A missing or malformed date, a future-dated bucket, a purchase with unknown historical use, and a disputed root cannot be treated as a known zero merely because an old normal window has ended. Provider spend is a separate cumulative ledger with no automatic monetary reset.

## Minimally safe paths for a release decision

| Path | What it achieves | Conditions and limits |
| --- | --- | --- |
| Keep new AI disabled | Deploy/review non-AI functionality while preserving every purchase, usage row, issue, and provider ledger entry. | Confirm that affected clients receive a deliberate 503 rather than an apparent successful paid AI service. This is an availability/product decision, not usage reconciliation. Reading/reviewing saved content should remain available. |
| Reconcile each historical case from evidence | Preserve original records; establish subject/root and conservative current-window count where independent evidence permits. | Requires a private case register, verified Apple history and server-owned binding/claim history, old request/provider logs if available, and a reviewed exact-once transformation on a restored copy. Do not infer an owner from `DeviceUuid`, copied JWS, row proximity, or a blank usage table. Some past calls may be unobservable. |
| Prospective UTC cutover after old writers stop | Avoid assigning unverifiable *past-window* paid calls to a current daily/minute budget. Keep original counters and issue history for audit. | Obtain a reliable timestamp for the last old writer/provider attempt, stop all old writers, and start only after the next UTC day plus any in-flight attempt window. Validate no future/invalid windows, no current-window ambiguous usage, and every accessible subject/root under the new contract. A reviewed code/data procedure must record why each issue is prospectively irrelevant and must keep unresolved ownership/purchase cases denied. The current global `Ready` gate cannot express this safely by itself. Requires explicit product/risk approval; no code or migration for it exists. |

The last path could resolve *historical usage-window* uncertainty without inventing historic ownership, because a future window starts with no prior calls from old writers. It does **not** create original-owner authority, desktop claims, mobile grants, or a clean Apple purchase. Existing `legacy_unproven` purchases stay unproven; paired Apple evidence may establish only the supported finite mobile restore. Unknown owner/root, legacy markers, token conflicts, and malformed/future usage require their own disposition. Any operational procedure must preserve the original `ai_usage`, imported `usage_buckets`, `usage_imports`, purchase records, and issue history, document each decision, and be tested against a restored production copy. A direct `UPDATE usage_accounting_state SET Ready=true` would bypass the intended fail-closed check while leaving unresolved subjects reachable.
