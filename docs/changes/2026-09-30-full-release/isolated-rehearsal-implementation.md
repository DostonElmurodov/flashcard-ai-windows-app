# Isolated migration rehearsal implementation

Status: local tool revised for the three findings in `isolated-rehearsal-review.md`; pending independent re-review. No live rehearsal, Docker container, database, SSH command, image pull, deployment, or workflow edit was performed by this subtask.

Backend checkout: `test-results/paid-access-hardening/backend`.

New files: `ops/linux/isolated-rehearsal.py` and `ops/linux/test_isolated_rehearsal.py`. The reviewed backup helper and workflow were not edited.

The one-off runner accepts only a canonical deployment path, backup ID, exact `ghcr.io/dostonelmurodov/mavrylo@sha256:<digest>` identity, and 40-character expected source revision. It requires the existing private archive and manifest beneath `.owl-ai-private-backups`; validates owner, modes, no symlinks/hardlinks, manifest size and fields, SHA-256, compatible PostgreSQL major, and `pg_restore --list`; and captures the live Compose API identity before any rehearsal container starts. It enforces 768 MiB memory caps on each new PostgreSQL/API container plus a 3 GiB host `MemAvailable` reserve and conservative disk reserve. Image pulls are followed by another resource check.

The official `postgres:<major>` image is resolved to a registry digest before use. The PostgreSQL container uses `--network none`, no published ports, one CPU, a process limit, and random rehearsal database credentials. The private archive is fed to `pg_restore --no-owner --no-acl --single-transaction` inside that uniquely named container; no live database connection or credentials are read. The backup contract can accept a newer restore client than the database major, so this runner now rejects that combination before any container creation; its in-container restore client must match the manifest's major. The candidate API starts with the exact pulled digest, sharing only that PostgreSQL container's network namespace, with no published ports or mounts, its own memory/process caps, random JWT, `ASPNETCORE_ENVIRONMENT=Production`, `TestMode=false`, real protection guards enabled, `AiSpend=false`, and isolated dummy Apple identity. Provider and Apple signing keys are blank. The script verifies image revision, namespace, `/health`, applied migration count/head, unchanged aggregate devices/subscriptions/legacy usage/words, `usage_accounting_state.Ready`, migration version, and only reviewed grouped issue reasons. It never sets `Ready`. The expected current source head is 14 migrations ending at `20260929161053_AddDeviceWordClientOrder`; the backup's pre-migration count is measured rather than assumed.

Docker's actual data root and each created PostgreSQL volume source are measured independently from the backup directory. The runner checks all distinct filesystems before pulls, before PostgreSQL start, during pulls and restore, during startup health polling, and after each stage; a breach aborts the active client and then stops the owned containers. Both rehearsal containers use Docker's `none` log driver to prevent container log growth. This is a monitored abort with bounded polling, not a hard filesystem quota. If Docker storage paths cannot be measured with the deployment user's permissions, the run fails closed.

The run's private 0600 JSON record keeps exact randomized container names, IDs, volume identifiers, and aggregate results. Docker `create` and `start` are separate: the ID is recorded before start. If a create response is lost, cleanup resolves only the exact random name with matching run/kind labels, immutable image ID, and network. SIGTERM/SIGHUP enter the same cleanup path; the cancellation handler remains installed until cleanup completes, and a signal received during cleanup is reported as failure after both stop attempts. Evidence-write errors are recorded independently and cannot skip a proven owned container's stop. Cleanup attempts both containers even if one stop or record write fails, retains stopped containers, volumes, archive, and private record, and reports failure if ownership or stop state cannot be verified. SIGKILL is uncatchable; the private names/IDs support manual recovery. Public output is restricted to fixed status and aggregate fields; raw SQL/data/container logs are not printed. The live API identity is checked before, during, and after the isolated run. Old-image compatibility on the migrated schema remains a separate release gate; candidate health plus aggregates cannot prove physical Apple purchase flows or paid-provider behavior.
