# Backend release preflight — 2026-09-30

Scope: read-only review of backend checkout `a6e2362c8e624338c564bfd88499cd1835c956c1`. No production database, server configuration, image, or deployment was changed by this review. The handoff reports 811/811 local tests passing; this report does not treat that as production readiness.

## Decision-critical facts

1. **Current production state must be measured before cutover.** Root's live read-only HTTP probe reported `health` OK and `test_mode: true` on the previously deployed backend. The new `Program.cs` rejects `TestMode:Enabled=true` in every non-Development host **before** calling `Database.MigrateAsync()`. That probe is historical deployed behavior, not evidence that the new release has disabled test mode. Confirm effective `ASPNETCORE_ENVIRONMENT`, `TestMode__Enabled=false`, image digest/SHA, and relevant non-secret configuration on the server without printing keys.
2. **The new server migrates the database on startup.** Freeze old writers before starting it. Capture a verified PostgreSQL backup, restore it into an isolated copy, and rehearse actual API startup through all pending EF migrations. Compare migration history and aggregate inventories before/after. A code/image rollback does not reverse schema changes. In particular, `AddDeviceWordClientOrder` explicitly aborts if `(DeviceUuid, ClientWordId)` duplicates exist; run `backend-inventory-before.sql` first.
3. **Historical usage may deliberately disable all AI.** `AddStableOperationUsage` imports old counters, records ambiguity in `usage_reconciliation_issues`, and creates `usage_accounting_state.Ready=false` if any issue exists. It creates a `historical_paid_usage_unknown` issue for **every existing subscription in that database**, including Sandbox/LocalTesting rows if mixed into Production. `OperationQuotaService.TryReserveAsync` rejects all AI while `Ready != true`. There is no operational clearing/reconciliation implementation in this checkout. If the live database contains subscriptions of any Apple environment, a successful migration/start/health check still leaves AI denied until a separately reviewed, evidence-based reconciliation procedure is completed on a restored copy and then applied safely. Do not directly flip `Ready`, erase issues, reset counters, or infer historical paid usage from a UUID.
4. **Paid ownership migration is additive but changes old-client behavior.** `AddAnonymousPurchaseRestore` gives each installed key its own owner and legacy purchases separate `legacy_unproven` owners; it deliberately grants no mobile authority from a historical UUID. Old clients that send only a UUID/raw transaction JWS cannot obtain new owner/mobile restore authority. New iOS must send the paired locally signed transaction and app-transaction envelope with fresh App Attest assertion. Inventory affected installed versions and legacy purchase classes, and validate recovery before enforcing the new path. A restored phone without original owner proof cannot first-claim desktop access. Retained read/review and deletion should continue under the approved content policy.
5. **Real numerical policy is still missing.** `AiOperationQuota:FreeDailyLimit`, `PaidDailyLimit`, and `PaidMinuteLimit` must be approved positive integers; `FreeMinuteLimit` is optional, but if present must be positive. These new keys are absent from `ops/linux/owl-api.env.example`; the older `AiProtection__FreeDailyQuota=40`, `AccountAi__DailyQuota=200`, and `AccountAi__RequestsPerMinute=30` examples are not approved D2 limits for the new operation guard. Missing new limits return `ai_quota_unconfigured` and deny AI. Free/trial/premium/grace and global guest policy require an explicit reviewed choice; do not treat sample/test numbers as approval.
6. **Provider spending is closed by default.** The env template sets `AiSpend__Enabled=false` and every amount/cap to zero; new real provider attempts then return 503 while saved read/review remains available. To enable it, approve cumulative integer micro-USD `GlobalMicroUsd`, `GuestMicroUsd`, `AccountMicroUsd`, plus positive `MaxConcurrentAttempts`, `MaxPromptBytes`, `MaxImageBytes`, `MaxOutputTokens`, `MaxResponseBytes`, `DeadlineMilliseconds`, `Enabled=true`, and reviewed `PriceProfile=2026-09-27-model-ceilings-v1`. The source bounds the last five transport sizes/deadline; the docs' synthetic 512-output example is not an allowance. Verify OpenAI/Gemini model, key, and current price-profile assumptions; unknown outcomes retain money and concurrency slots. No automatic budget reset or live ledger repair is implemented. Do not increase/reset balances to cure a denial.
7. **Server identity and purchase settings need live verification.** Check non-secret presence/correctness of JWT issuer/audience and key length, trusted forwarded proxy, `AiProtection__Enabled=true`, `AiProtection__RequireAssertion=true`, `Apple__SkipSignatureValidation=false`, `LegacyAuth__Enabled=false`, exact Apple bundle/product IDs and trusted environment, readable server-only `.p8` and issuer/key IDs, and `Apple__AppStoreServer__AppAppleId` set to the real positive App Store app ID. The last key is absent from the env example but required for new AppTransaction verification. Production and Sandbox/App Review need separate API, database, credentials, usage counters and budgets; both run with host Production and test mode false.
8. **Exact-image deployment is not guaranteed by the current workflow.** `.github/workflows/api-ci-cd.yml` `workflow_dispatch` builds/tests/pushes `latest` and a SHA tag, then SSH runs `docker compose pull && docker compose up -d`; `ops/linux/README.md` shows Compose using mutable `latest`. A concurrent push can change `latest` between validation and pull. Pin Compose to the tested SHA/digest, verify the running digest and commit, and keep the previous image plus database restore plan. The manual dispatch is a publish-and-deploy action, not a harmless validation run. The workflow's `.NET 10.0.x` and floating base image also do not prove the exact runtime used in local transport tests.

## Minimal read-only inventory

Run [backend-inventory-before.sql](backend-inventory-before.sql) on each authorized **pre-migration** database, and the repository's `ops/audit-subscription-state.sql` with trusted server-side expected environment and allowed product IDs as shown in `docs/paid-access-rollout.md`. Both produce aggregate counts only. Keep any private case-level reconciliation in a controlled register. On the restored copy after migration, run [backend-inventory-after.sql](backend-inventory-after.sql). The latter exposes only readiness, issue reasons/counts, conflict counts, and spend aggregates. It cannot by itself prove a purchase is legitimate or that a pending provider charge can be released.

The production cutover needs successful backup/restore and startup rehearsal, a reviewed disposition of all aggregate anomalies and `Ready=false`, approved D2 values and spend envelope, effective server configuration, an exact tested image, and a coordinated new-client transition. A live HTTP health check alone proves only that the process responds. Physical iPhone/App Attest/StoreKit and Sandbox route checks remain prerequisites for an Apple release; they are separate from whether the Windows package can be built or signed.
