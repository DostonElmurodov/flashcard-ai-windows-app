# Local isolated migration rehearsal route

Status: local implementation frozen for independent review. This subtask did not run Docker, load an image, decrypt or read a real backup, restore a database, contact the original server, or edit the deployment workflow/export job. No rehearsal result is claimed.

New file: `test-results/paid-access-hardening/backend/ops/linux/local-rehearsal.py`, with focused `test_local_rehearsal.py`. The accepted server rehearsal runner gained only shared private-backup validation and an option to inspect an already-local PostgreSQL image without pulling it. Its Compose/live-identity path is unchanged.

The explicit local CLI takes a private directory, backup ID, pinned plaintext SHA-256, candidate registry digest, expected source revision, and pinned offline config image ID. The private directory must be canonical, owned by the caller, and mode 0700; the archive and manifest must be 0600 regular files with one link. The archive is hashed against the caller's plaintext pin **before manifest parsing or `pg_restore` listing**. The existing manifest contract then checks ID, archive basename, size, hash, PostgreSQL/dump/restore majors and validation marker. The local route requires PostgreSQL 16 and uses `pg_restore --list` from its isolated PostgreSQL 16 container, because WSL has no host restore client.

The PostgreSQL image must already be local as `postgres:16` with a verifiable official RepoDigest; the script does not pull it. The candidate must also already be local. If Docker retains the exact `ghcr.io/dostonelmurodov/mavrylo@sha256:<digest>` RepoDigest, the script checks that digest, the pinned config image ID, and OCI source revision. A `docker save`/`docker load` route may lose RepoDigests; then the script inspects and runs only the explicitly pinned immutable config image ID and verifies its revision. Both PostgreSQL and API creation commands use `--pull=never`, so image removal after inspection fails closed. The registry digest-to-config-ID mapping in this fallback comes from the trusted export job and the coordinator's independent archive-hash/load verification; the local runner does **not** claim to cryptographically establish that mapping or accept a mutable tag.

The new PostgreSQL container uses `--network none`, no published ports, no Docker logs, a 768 MiB memory cap, one CPU, a process limit, random rehearsal database/user/password, and its own Docker volume. After it starts, capacity checks run **inside that container** using fixed `stat -f` queries for both the container overlay (`/`) and PostgreSQL data volume (`/var/lib/postgresql/data`). This avoids treating Docker Desktop VM paths as WSL paths. Both Docker filesystems and the private backup filesystem must keep conservative reserves. The monitor aborts image/restore/startup work on an observed breach; it is not a hard filesystem quota and can overshoot between probes. The script retains stopped containers and the volume for diagnosis.

The private archive restores with `--no-owner --no-acl --single-transaction` only to that new container. The exact candidate config image ID starts as an API container sharing only the PostgreSQL namespace, with no mounts/ports, 768 MiB cap, Production hosting, TestMode=false, protection/assertion guards enabled, AiSpend=false, fresh JWT, dummy Apple identity, and blank provider/signing keys. A local network-namespace HTTP probe checks `/health`; aggregate read-only SQL checks the original copy before and after actual startup migrations. It requires 14 applied migrations ending at `20260929161053_AddDeviceWordClientOrder`, preserved devices/subscriptions/legacy usage/words counts, migration version 1, and observed `usage_accounting_state.Ready` consistent with whitelisted issue counts. It never sets Ready. Public output explicitly says `rehearsal_scope=local_copy` and `rehearsal_original_server_accessed=false`; it reports only fixed identities/status/aggregate fields. Private 0600 evidence holds container/volume identifiers and aggregate results. Existing exact-name/label ownership recovery and cancellation-protected cleanup are reused.

Local verification: 18 mocked tests passed under WSL Ubuntu Linux with zero skips (`python3 -B -m unittest ops/linux/test_local_rehearsal.py ops/linux/test_isolated_rehearsal.py`). The same suite passed on Windows with two platform-specific skips. Python syntax compilation passed. Tests cover the plaintext-pin ordering, Linux ownership/mode rejection, exact digest versus pinned offline ID, both Docker Desktop capacity probes, invalid-pin early exit, both no-pull creation commands, and shared lifecycle/cleanup failures. They do not prove Docker image content, actual restore/startup, or purchase/provider flows. The original server's roughly 400 MiB available memory is below the unchanged 4.5 GiB host floor, so the server route remains blocked; this local route makes no live-server stability claim.
