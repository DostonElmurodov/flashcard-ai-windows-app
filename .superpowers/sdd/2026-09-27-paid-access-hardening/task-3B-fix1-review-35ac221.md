## Important residual I5-A — a late older processor suppresses the newer response

Primary: [StoreKitService.swift:401](<D:/07 Hobby/FlashcardAI/test-results/paid-access-hardening/ios/Infrastructure/Purchases/StoreKitService.swift:401>), with the drop at [StoreKitService.swift:427](<D:/07 Hobby/FlashcardAI/test-results/paid-access-hardening/ios/Infrastructure/Purchases/StoreKitService.swift:427>).

The captured authority is correctly older, but entering `processPurchaseEvidence` always installs a new global `refreshRevision`. An older operation that reaches this method late can therefore invalidate the processor of a genuinely newer operation already awaiting its response. The newer captured authority does not help because the response exits on `refreshRevision` before applying it.

Deterministic source reproduction using the existing fake seams:

1. Start discovery A. It captures authority order 1, then suspend its `currentOperation` before any processor starts.
2. Start `processPurchaseEvidence` B. It captures order 2, writes refresh ID B, and reaches an independently gated backend response. Keep B pending.
3. Release A's enumeration with valid evidence. A enters the processor with its original order 1, but overwrites `refreshRevision` with ID A. Return A's valid inactive/history response. With no newer accepted authority yet, order 1 is current and A applies it.
4. Release B's successful premium response. B can finish its durably acknowledged transaction, but line 427 sees ID A and returns `backendAcknowledged=true, appliedToCurrentSession=false`. The newer premium confirmation is discarded and the older state remains.

This does not require key/account changes, a failed backend response, or a narrow race inside an individual statement. It requires only the permitted overlap of enumeration and transaction processing. The same global revision can also let a later-entering stale processor suppress newer processor error handling.

The saved tests at [AnonymousPurchaseRestoreTests.swift:867](<D:/07 Hobby/FlashcardAI/test-results/paid-access-hardening/ios/FlashCardAITests/AnonymousPurchaseRestoreTests.swift:867>), lines 893 and 965 wait for B to be **accepted** before releasing A. The repaired M1 test starts the old processor before the new one. Neither establishes the schedule above, where B starts first and remains pending while older A reaches the processor later.

Repair expectation: processor-arrival UUIDs must not reverse captured operation ordering. Preserve durable acknowledgment/finish while deciding application using the original ordering model. Add a gated regression with A enumeration held, B backend held, A applied first, and B released last; B's newer response must apply. This is a source finding; no such runtime test was executed in this review.

## Important residual I5-B — the authority predicate becomes stale across its own await

Primary: [StoreKitService.swift:126](<D:/07 Hobby/FlashcardAI/test-results/paid-access-hardening/ios/Infrastructure/Purchases/StoreKitService.swift:126>).

`stillCurrent` checks `isCurrentAuthorityRequest` at line 128, then awaits `accountSessionGeneration()`. After that suspension it checks only the returned account generation and key. It does not recheck authority/identity. Main-actor isolation does not make the region spanning that await atomic. The production default crosses `APIClient.accountSessionGeneration()` and the account session actor; the injected closure also makes the schedule deterministic.

Reproduction: let old discovery A throw an evidence error and enter the catch at lines 314–315. Suspend the account-generation lookup **inside** A's `stillCurrent`, after its authority check passed. Complete newer B successfully, accepting a higher order and clearing errors. Resume A's lookup with the same account generation/key. `stillCurrent` returns true and A writes its old error over B's success.

The same predicate is used after response revision checks at lines 427–432 and 518–519. A newer result can apply during this wait; the old path can then persist its stale token before `EntitlementStore.update` performs its own final authority check. That store check protects its entitlement update, but it does not undo token persistence or error writes. No backend authorization bypass is inferred.

The saved tests hold evidence/purchase/backend work, not this final predicate's account-generation lookup. They therefore do not cover the check-then-suspend gap. Recheck key, identity/order and the relevant response/busy owner after the final await, immediately before side effects; retain final store guards as well. Add a deterministic injected-generation suspension test for the error path and a token-persistence assertion for a success path. No new runtime result is claimed.

## New breakage in the fix diff

### N1 — Important: later envelope success clears an unresolved earlier reconciliation failure

Primary: [StoreKitService.swift:265](<D:/07 Hobby/FlashcardAI/test-results/paid-access-hardening/ios/Infrastructure/Purchases/StoreKitService.swift:265>) and [StoreKitService.swift:287](<D:/07 Hobby/FlashcardAI/test-results/paid-access-hardening/ios/Infrastructure/Purchases/StoreKitService.swift:287>), composed with [StoreKitService.swift:441](<D:/07 Hobby/FlashcardAI/test-results/paid-access-hardening/ios/Infrastructure/Purchases/StoreKitService.swift:441>).

The new loops retain `firstFailure` and continue processing other transaction IDs. A later applicable success clears `errorText` in the shared processor. Returning `firstFailure` does not restore its guidance: explicit Restore simply returns false at line 492; foreground only refrains from clearing the already-cleared error at line 523.

A concrete multi-chain scenario is current purchase C acknowledged, then unfinished purchase A from a different original receives `subscription_reconciliation_required`, then unfinished purchase B from another original is durably acknowledged. After A, `firstFailure` is set and support guidance is displayed. For B, `continuingOperation` issues the next same-operation authority; successful processing clears that guidance. Discovery still returns A's failure. Explicit Restore returns false with `errorText=nil`; [PaywallView.swift:313](<D:/07 Hobby/FlashcardAI/test-results/paid-access-hardening/ios/Presentation/Features/Home/Views/PaywallView.swift:313>) copies that nil error, so the unresolved reconciliation has no explanation. Public refresh likewise preserves nil rather than the failure.

A simpler fake regression can use two distinct restoration originals, first failing and second succeeding. For fidelity to the current/unfinished product path, use the current-plus-two-unfinished scenario above. A successful check for another original is not evidence that A's reconciliation was resolved. The original code stopped on the first processing error; this continue-and-clear composition is introduced by the fix.

Keep acknowledgment/finish of the other valid transactions, but derive visible discovery failure from the retained unresolved outcome after processing, with the same operation-order guards. Clear reconciliation only after an applicable recovery resolves it. Add a failed-envelope-then-successful-other-envelope public Restore/foreground test. This finding concerns lost failure guidance; it does not claim that another independently valid purchase must be denied or that the server permits paid use of a quarantined purchase.

No new Critical or separate Minor source finding is established in the remaining diff. N1 is also why I4 cannot be marked fully closed; it is not counted as a second independent copy of that open area.
