## Implemented boundary

- New registration ignores caller `device_uuid`, creates a random server compatibility namespace and an independent installation owner in one transaction. A fresh, verified same-key attestation returns a token while preserving original key material, environment, owner, UUID and counter; changed material returns `registration_conflict`. Concurrent insert loser rereads the committed winner. Replayed bootstrap returns 403 `invalid_device_proof`.
- Additive `AddAnonymousPurchaseRestore` migration and snapshot create four entities/tables, device owner FK and subscription Apple metadata. The populated-copy backfill gives each historical device an independent owner and each structurally recognizable purchase a separate `legacy_unproven` owner/binding. It imports no historical UUID as token, creates no mobile grants, and preserves account claims/tombstones and usage. `AnonymousPurchaseTokenEntity` is schema only in this slice.
- `AppAttestProofService.VerifyAsync` consumes the bound challenge, verifies the exact v1 body/path/key hash and stored public key/counter, and conditionally updates from observed old counter to a greater value. A losing update returns `invalid_device_proof`. Both assertion filters use this boundary; account claim still forwards through the IAP filter. Proof consumption occurs before route business actions and is not enclosed in their later transaction.
- `POST /owlai/app-attest/resume` accepts an empty object or zero-byte body as actually transmitted, rejects fields/nonobjects, buffers and rewinds at 16,000 bytes, uses the stored key assertion without bearer, and returns the existing device token response with `Cache-Control: no-store`. Unknown key is 401 `invalid_device`; rejected proof is 403 `invalid_device_proof`.

## Acceptance coverage and limits

Registration tests cover a victim UUID, changed caller UUID, same-key high-water preservation, changed public key/environment, concurrent insert, replay and B1. PostgreSQL proof tests cover same-counter concurrent assertions in separate contexts, smaller delayed counter, replay, wrong key/path/body hash, and unchanged high-water. The IAP filter is exercised directly in the race test; existing AI filter and account-claim tests pass after routing through shared proof; resume is exercised by HTTP without JWT. The migration fixture covers shared historical UUID, linked account, null-owner claim tombstone, valid/quarantined environments, daily and minute usage, saved word, paid marker, counter and reapplication. The test uses a verifier constrained to a hand-computed body hash for tamper coverage; no real Apple proof is claimed.

The migration's structural recognition of historical purchases uses a known Apple environment, nonblank product/ID and finite expiry. It cannot evaluate deployment-specific product allowlists at migration time; 2B.2 still performs canonical Apple validation before grant or owner authority. There is no dedicated new test for business-action rollback after proof; code order and the existing filter path show proof update before action, and independent review should check this. The migration test was added after generated schema/backfill rather than observed RED; core registration, race, resume, replay and error-code behaviors each have saved behavioral RED and GREEN evidence. This is a TDD process gap, not a claim of a migration RED run.

Existing test changes preserve security expectations: the B1/B2 assertions were not inverted. The B3 HTTP fixture opts into a fake verifier that returns `storedSignCount + 1` for each fresh valid assertion; this models the monotonic real verifier and keeps the 10-word/provider-count assertions. The AI filter test now reads high-water `AsNoTracking` because EF `ExecuteUpdate` leaves its tracked object stale. The bootstrap tests expect the frozen 403 proof error instead of prior 401; the public set route test asserts the stable `code` rather than old error prose. No test-mode or provider bypass was added.

Manual simplify passes after each implementation cycle: (1) registration kept one `SameKeyResult` and one token response builder, with caller UUID removed from assignment; (2) shared proof removed duplicate challenge/verification/counter writes from both filters while retaining their different body limits; (3) resume uses one empty-object shape check and exact bytes, without a reserializing DTO; (4) migration uses one backfill pass per historical class and no guessed UUID join; (5) fixture repair made advancing counters opt-in only, leaving rejection fakes unchanged; (6) stable error mapping reused existing filter response helpers and left commercial gates untouched. Final self-review found no whitespace errors or EF model drift. The principal remaining concern is that staged schema and old IAP resolver coexist only until 2B.2; this commit must not be deployed alone.
