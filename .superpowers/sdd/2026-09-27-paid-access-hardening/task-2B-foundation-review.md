### Important — I1: finish the registration error contract

[AppAttestRegistrationService.cs:82](<D:/07 Hobby/FlashcardAI/test-results/paid-access-hardening/backend/src/Mavrylo.Services/Services/AppAttestRegistrationService.cs:82>) still returns HTTP 401 with only `{ error = ... }` when a fresh bootstrap challenge is accepted but `VerifyAttestation` rejects its proof. Other registration validation paths at lines 33, 47, 60 and 66 also return the old body without `code`. [DeviceController.cs:89](<D:/07 Hobby/FlashcardAI/test-results/paid-access-hardening/backend/Areas/OwlAI/Controllers/DeviceController.cs:89>) forwards those bodies unchanged.

The foundation brief explicitly requires register/result maps to use the frozen error contract; contract section 3 requires `{code,error}`, and section 5 distinguishes `401 invalid_device` recovery from `403 invalid_device_proof` challenge retry. Only rejected bootstrap challenges and conflicting same-key material were converted. A client following that contract cannot reliably classify rejected attestation versus invalid device identity, even though both requests are safely denied. This is a missed wire requirement, not an authorization bypass.

Normalize all registration failures to stable codes and map cryptographically rejected bootstrap proof to `403 invalid_device_proof`. Keep malformed input distinct with an agreed stable validation code. Add focused service/HTTP assertions for verifier rejection and malformed registration so status, `code` and `error` are checked together. Assertion-challenge's existing unknown-key 401 at line 139 likewise lacks `invalid_device`; include it if centralizing the shared device result mapper.
