# Task 11 research: iOS hosted UI assertions

Research only; inspected checkout `4bb69cb` and the fixed-source `9096c1e` baseline artifacts. No code, test target, index, branch, or Mac run was changed. The baseline records 545 tests: 517 passed, 24 failed, 4 skipped. Of its failures, 20 are hosted SwiftUI UI cases in six groups; the other four are API fixture cases outside this task. The four skips are `AccountViewTests` UI cases. Source: `task8-results/ci-baseline-full-cases.json`, `ci-baseline-full-full.log`, and `ios-full-suite-preflight.md`. The current-head full run belongs to the controller and was not used to infer a result here.

## Decision

Use a real XCUIAutomation UI-test target with a **Debug-only deterministic app fixture** for the UI contracts. Keep state/model tests in the existing unit-test target. A public-API change to `UIWindow` or to the recursive `NSObject` traversal is worth at most a small diagnostic probe, not a defensible fix for all 24 cases: `LibraryViewHostedTests.hostInWindow` already attaches to an available `UIWindowScene` (`FlashCardAITests/ApplicationBehaviorTests.swift:4538-4555`), and `AccountViewTests.makeWindow` does likewise (`FlashCardAITests/AccountViewTests.swift:192-208`), yet both groups fail to expose the SwiftUI tree. Other hosted helpers use a bare `UIWindow` (`ApplicationBehaviorTests.swift:5192-5202`, `5406-5416`), so scene attachment may improve those particular fixtures but does not resolve the cross-group evidence. The traversal only calls `accessibilityElementCount` / `accessibilityElement(at:)`, then UIKit subviews (`ApplicationBehaviorTests.swift:4617-4653`, `5130-5185`; `AccountViewTests.swift:228-267`); an empty tree supplies no real element to assert or activate. The baseline log includes empty labels and nil unwraps, while non-AX hosted assertions still pass (for example, `LibraryViewHostedTests.testEntryAndPullEachInvokeOneCoordinatedRefresh` at `ApplicationBehaviorTests.swift:4295-4331`). This indicates a harness visibility problem, not proof that app controls are absent or that every UI behavior is correct.

The project currently has only an app-hosted **unit-test** bundle, `FlashCardAITests` (`FlashCardAI.xcodeproj/project.pbxproj:803-819`, `1211-1252`); there is no UI-test target. Apple describes UI tests as a separate process that queries and interacts with the app through accessibility: [User Interface Testing](https://developer.apple.com/library/archive/documentation/DeveloperTools/Conceptual/testing_with_xcode/chapters/09-ui_testing.html), [XCUIAutomation](https://developer.apple.com/documentation/xcuiautomation), [XCUIElementQuery](https://developer.apple.com/documentation/xcuiautomation/xcuielementquery). `UIHostingController` documents UIKit integration, not enumeration of all internal SwiftUI accessibility nodes by hosted unit tests: [UIHostingController](https://developer.apple.com/documentation/swiftui/uihostingcontroller). Changing Xcode or runtime would test another environment; it would not establish that UI assertions work on Xcode 26.6 / iOS 26.4.1.

## Bounded follow-on implementation and proof

1. Add an iOS UI-test target to the current scheme. First prove one existing control, such as `Search Learn`, is found, tapped, and changes the displayed field on **Xcode 26.6 / iOS 26.4.1**. If XCUI cannot see it, inspect an actual XCUI hierarchy/screenshot and repair app accessibility semantics; fail the test rather than skipping it. Use `waitForExistence(timeout:)` for asynchronous appearance ([Apple](https://developer.apple.com/documentation/xcuiautomation/xcuielement/waitforexistence%28timeout%3A%29)).
2. Add a launch-argument-selected, `#if DEBUG` fixture path at app composition/bootstrap, with fresh isolated database/defaults and deterministic seeded cards, sets, onboarding/account states, and fake API/StoreKit action dependencies. UI tests pass fixture names via `XCUIApplication.launchArguments` ([Apple](https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/launcharguments)). The existing app root instantiates composition before its scene body (`App/FlashCardAIApp.swift:24-28`; `App/Root/AppRootModel.swift:65-91`), and `AppComposition.make` currently creates a real `APIClient`, StoreKit service, account session, and default transaction-update source (`App/DependencyInjection/AppComposition.swift:19-41`, `66-79`); therefore the fixture must intercept startup **before** those defaults or inject inert substitutes throughout. A later `.task` guard (`FlashCardAIApp.swift:107-135`) is insufficient to prove no live calls. Keep real auth, paid entitlement, and Release behavior unchanged; synthetic purchase outcomes are UI-flow fixtures, never authorization evidence.
3. Add stable accessibility identifiers only where labels are ambiguous or localized; preserve user-facing labels and VoiceOver semantics. Several account/settings controls already have identifiers (`Presentation/Features/Account/AccountView.swift:148-149`, `247-248`, `274`; `Presentation/Features/Settings/Views/SettingsView.swift:135`, `172-174`). Apple documents identifiers for testing: [SwiftUI accessibilityIdentifier](https://developer.apple.com/documentation/swiftui/view/accessibilityidentifier%28_%3A%29). Use real XCUI queries/taps/typing and assert visible results, including negative assertions only after a positively established screen state.
4. Port the 20 cases and four AccountView cases in small groups, retaining the named UI contracts and appropriate state unit checks above. Remove the old in-process AX test bodies and the four skips only when corresponding real UI tests pass; preserve non-AX unit tests. Run focused UI tests, full unit + UI suite on the current runner/runtime, and a Release-build check that the fixture path is absent. Capture actual case counts and failures; do not claim full resolution from a green subset.

Limit: this is a source-and-baseline recommendation, not a demonstrated XCUI result. It does not diagnose whether every original hosted case has a second behavioral bug once the app is queried externally. Fixture isolation, accessibility snapshots, and full current-runtime runs are the necessary proof.
