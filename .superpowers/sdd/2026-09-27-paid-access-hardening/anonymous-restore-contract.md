# Anonymous purchase ownership and ordinary Apple restore — executable contract

Date: 2026-09-28. Approved behavior authority: `anonymous-restore-approved-behavior.md`. This replaces the account-mandatory design in historical Tasks 2/3; it does not reopen the approved behavior. Read `anonymous-purchase-design-research.md` for the already-established replay limitation. No product code or tests were changed to produce this contract.

## 1. Authority and scope (frozen interface for Task 2B)

An installation is an App Attest public key. A server-created anonymous owner is a durable purchase principal. A purchase is `(environment, originalTransactionId)`. A mobile grant permits that installation to use that purchase on iPhone only. An Owl session separately permits private account data and, for an already linked purchase, desktop entitlement. A quota subject is accounting state, never an authentication credential.

The initial attested installation controls its newly server-created anonymous owner. Its assertion authorizes purchase-context issuance and first desktop claim for purchases actually bound to that owner. No separate recovery secret, synchronized key, passkey or recovery-code product is introduced. A new installation always gets a new owner; a restored purchase can belong to another owner. The restore grant must never replace `Device.AnonymousOwnerId`, create an owner-authorized installation, rotate an owner credential, or disclose another installation/account's saved content.

Normal reinstall/new-iPhone restore requires no original key, old phone, Owl login or recovery code. It establishes the narrower mobile grant using the verified Apple envelope in section 4. First desktop claim after all original owner-authorized keys are lost is a separate exceptional recovery case. Existing linked-account login continues normally. There is no automatic receipt-to-desktop first claim and no invented support recovery backend.

`DeviceUuid`, `appAccountToken`, original transaction ID, app transaction ID, grant ID and JWT entitlement claims are references, never standalone authority. Mobile login/logout must not reset rights, quota or paid history. No new trial is minted.

Use existing `Devices`, `Subscriptions`, account-link fields and Task 4 Apple state machinery. Add:

| `MobilePurchaseGrantEntity` / `mobile_purchase_grants` | Composite PK `DeviceId, Environment, OriginalTransactionId`; binding FK; `VerifiedAt`, `ValidUntil` UTC, nullable `VerifiedAppTransactionId`, `EvidenceKind` (`paired_device` or `paired_device_legacy`), `LastEvidenceHash`. Do not change the existing `Subscriptions` PK in this chunk. Its original-ID collision across environments fails with `subscription_reconciliation_required`; never overwrite a Sandbox row as Production. Continue Task 4's advisory lock keyed on original ID (namespace 431), which also serializes that collision. New tables have restrictive/no-cascade owner and purchase FKs. Preserve existing `OwnerAccountId`/`ClaimedAt` arbitration and tombstone semantics; null account plus non-null timestamp remains claimed/deleted. Account deletion removes account data/sessions as today, preserves binding/grants/paid history, clears only the existing live account FK, and leaves the claim timestamp and accounting lineage.

New registrations use a random server-owned `DeviceUuid` only as a compatibility library namespace. Ignore caller `device_uuid` for all joins and authorization. Keep historical values unchanged for reconciliation. `EntitlementService.UpsertAsync` becomes state-only: retain its signature temporarily for callers if needed, but `relinkDevice` must have no ownership/enrollment effect; remove both current relink branches. New verified subscriptions must not project the Apple token into `DeviceUuid`.

Migration creates tables/nullable columns, backfills one owner per existing device, and creates one `legacy_unproven` owner/binding per existing applicable purchase without inferring an installation owner from UUID. Existing account claims remain valid; unclaimed legacy purchases have no proven first-desktop claimant. Do not import a historical token from overwritten `DeviceUuid`. No purchase/card/tombstone/usage deletion. Environment-invalid historical rows remain quarantined by Task 4. Migration application twice and startup after migration must preserve row counts, sticky paid history, link timestamps and counter high-water marks.

## 3. HTTP and proof contract (Task 2B)

All new JSON uses existing snake_case policy; UUID wire format lowercase canonical `D`. Reject duplicate semantic JSON fields in new DTOs and unknown authority-like fields; no owner/account/usage ID accepted where not specified. Existing compatible optional fields remain only where stated. All IAP/context/resume/claim responses use `Cache-Control: no-store`. Errors have `{ "code": "stable_code", "error": "plain message" }` without foreign owner/account identifiers.

Foundation review clarification (I1, root ruling): malformed registration fields/base64 return `400 invalid_registration_request`; rejected bootstrap/attestation or unavailable simulator proof returns `403 invalid_device_proof`; same-key material conflict remains `409 registration_conflict`. Assertion-challenge unknown key returns `401 invalid_device`, malformed challenge request `400 invalid_request`. This names previously unspecified validation codes; it does not change successful registration or any purchase authority.

| Endpoint | Request | Authentication / response |
|---|---|---|
| Existing `POST /owlai/app-attest/register` | Existing `AppAttestRegisterRequest`; legacy `device_uuid` ignored | Fresh verified bootstrap attestation. Atomically insert device+owner; retain existing `AppAttestRegisterResponse(device_token, expires_at)`. Same-key valid retries compare exact public key/environment, preserve original owner/library/public key/counter, and return existing identity's token. Different material: 409 `registration_conflict`. Reused challenge: 403 `invalid_device_proof`. |
| New `POST /owlai/app-attest/resume` | `{}` | No bearer required; existing assertion headers prove the named stored key. Returns `AppAttestRegisterResponse`. Unknown key 401 `invalid_device`; never creates a key/owner. This recovers a lost/expired device JWT without discarding a valid App Attest key. |
| New `POST /owlai/iap/purchase-context` | `IapPurchaseContextRequest(string ProductId)` | Device JWT + assertion. Allowed product required. `IapPurchaseContextResponse(Guid AppAccountToken)`; server gets/creates token for authenticated installation's own anonymous owner. No Owl login. If a different restored binding currently provides active access, return 409 `subscription_already_active` instead of encouraging duplicate purchase. |
| Existing `POST /owlai/iap/verify` | Existing `IapVerifyRequest(string JwsTransaction, string? DeviceUuid=null)`; ignore `device_uuid` | Device JWT + assertion. Strong owner purchase path only: signed token must equal a stored token of this installation's owner, or purchase already has a `server_token` binding to that owner. Raw/copy-only foreign or legacy proof: 403 `purchase_owner_proof_required`; use restore endpoint for mobile recovery. |
| New `POST /owlai/iap/restore` | `IapRestoreRequest(string JwsTransaction, string JwsAppTransaction, string DeviceVerificationId)` | Device JWT + assertion over all exact bytes. No Owl header required. Section 4 envelope verification establishes only mobile grant/history link. No arbitrary raw transaction-ID lookup route. |
| Existing `POST /owlai/iap/token`, `GET /owlai/iap/entitlement` | Existing empty request | Device JWT + assertion; resolve server owner bindings/mobile grants/account session. Never join subscriptions on UUID. |
| Existing `POST /owlai/account/subscription/apple/claim` | Existing `{account_id,jws_transaction}` | Account bearer + `X-Device-Authorization` device bearer + existing raw-body App Attest proof. Body account must match session. First claim requires installation owner equal to `server_token` purchase owner. An existing same-account claim is idempotent; different account/tombstone remains 409 `subscription_already_linked`. A mobile grant alone gives 403 `desktop_owner_proof_required`. |

`IapVerifyResponse` and `IapTokenResponse` retain existing fields and add `string PurchaseAuthority` (`owner`, `mobile_restore`, `none`) and nullable `string MobileGrantExpiresAt`. `EntitlementDto.ResolutionSource` is `device` for owner, `mobile_restore` for restored mobile, `account` only for an actually authenticated account; `PurchaseIsLinked` is a boolean, not an identifier. `WasEverPaid` remains sticky. These are client hints; every protected request resolves DB state. Use standard 200 for successful active or historical restore; the entitlement status describes active/expired/revoked. Do not manufacture free status for a recognized expired paid purchase.

Preserve the canonical assertion v1 preimage exactly:

```text
H = SHA256(nonceBytes || 0x1F || SHA256(exactRequestBodyBytes)
           || 0x1F || UTF8(exactRequestPath) || 0x1F || UTF8(challengeId))
```

Headers: `X-App-Attest-Key-Id`, `X-App-Attest-Challenge-Id`, `X-App-Attest-Assertion`, existing client-data-version header. JWT key must equal header key except resume, which authenticates directly by proof. Existing two-minute DB challenge TTL is retained, single use, bound to key and exact path; all new mutation routes are POST only. Empty resume/token body is exactly `{}` or zero bytes as actually sent and hashed, never reserialized on server. Bootstrap remains SHA256(nonce) because all authority-bearing registration state is assigned by server; a signed caller UUID would still prove no owner relationship.

Extract one `AppAttestProofService.VerifyAsync(string keyId, byte[] rawBody, string path, string challengeId, string assertionBase64, CancellationToken ct): Task<AppAttestProofResult>` used by IAP/account-claim, AI filter and resume. Result fields: `bool Ok`, `string? Code`. It consumes challenge atomically, verifies stored public key and old counter, then performs conditional `UPDATE Devices SET SignCount=new, LastSeenAt=now WHERE KeyId=key AND SignCount=old AND new>old`. Exactly one changed row authorizes continuation; no read/write last-writer counter rollback. A CAS loser uses a new challenge/assertion, never retries the accepted old proof. No business mutation runs before proof success. Counters/challenges stay consumed even if later business validation fails. Simulator bypass remains existing DEBUG+Development only, never enabled for Release, public restore, or tests pretending Apple validity.

## 4. Apple evidence and grant rules (Task 2B)

Use `AppleJws`'s existing pinned chain/ES256 checks; add an explicit app-transaction decoding path selecting `receiptCreationDate` for certificate-time validation, without weakening transaction/notification checks. No new cryptographic framework. `AppleMobileRestoreVerifier.Verify(IapRestoreRequest request): AppleRestoreEvidenceResult` produces either a typed verified evidence record or a stable failure. Its record is `VerifiedAppleRestoreEvidence(SubscriptionEntity Transaction, string? AppTransactionId, string EvidenceKind, string EvidenceHash)`; fake providers construct this record only in isolated tests.

For **both** JWSs verify signature and app identity. Transaction payload uses `environment`, `bundleId`, `productId`, `originalTransactionId`, finite `expiresDate`, `inAppOwnershipType`, optional `appAccountToken`, optional `appTransactionId`, and local `deviceVerification`/`deviceVerificationNonce`. AppTransaction payload uses `receiptType`, `bundleId`, `appAppleId`, `receiptCreationDate`, optional `appTransactionId`, and its own local device fields. Production requires configured positive `Apple:AppStoreServer:AppAppleId` matching the app payload. Expected environment/bundle/products remain Task 4 configuration. Both receipt and transaction environments must match. Missing signed date/device fields, invalid UUIDs, invalid base64 or non-48-byte digest are rejected; a server-fetched AppTransaction without local device fields cannot substitute.

For each JWS independently calculate `SHA384(ASCII(lowercase(nonce UUID D) + lowercase(submitted deviceVerificationId UUID D)))` and constant-time compare to its signed decoded `deviceVerification`. Both must match the same submitted device ID. If both signed `appTransactionId` values exist, require equality. If one/both are absent, paired signed device checks still support `paired_device_legacy`; do not require an iOS upgrade or own secret merely because this correlation field is missing. Explicit mismatches are 403 `restore_evidence_mismatch`; they are not treated as an absent field. The honest app uses only StoreKit `.verified` results and local `AppStore.deviceVerificationID`. A download/purchase Apple-account mismatch can require explicit StoreKit refresh and remains a physical-device compatibility gate, not a reason to guess ownership.

Fetch canonical status for the **same** original ID through existing Apple client, validating environment/product and finite expiry. Failure is 503 `apple_unavailable`, identity mismatch 503 `apple_identity_mismatch`; no new grant, owner binding, free fallback or paid extension. Missing `appAccountToken` is valid on restore/lifecycle paths (Family Sharing/old/external purchase), but never sufficient for new owner purchase binding or desktop claim. Remove the global token-required rejection from Apple projection and apply it in the strong new-purchase flow instead. Family-shared mobile access follows verified recipient evidence and that subscription's canonical status; no desktop first claim from a family grant and no token fabrication. Do not merge different family members by appTransactionId or claim family-wide quotas without an Apple-proven common purchase identity.

Transaction locking: perform external Apple calls before opening the DB transaction; then lock user first for claim (existing deletion order), purchase advisory lock next, installation/binding rows after. Under lock reread current state and apply Task 4's `LastAppleEventAt` ordering; a late proof never undoes newer revocation. For new strong purchases, bind once to the server token's existing owner after checking it equals the requesting installation owner. For restore, keep existing binding; if absent, use a known server token's mapped owner if present, otherwise create a `legacy_unproven` owner. This is only purchase bookkeeping: restore never gives the requester strong owner authority even when it creates that binding. Notification-before-client may create a state row, but no installation/grant/account link. First binding insertion and retry use the same lock/unique constraint.

Upsert grant only after canonical verification and state ordering. `ValidUntil` is the current verified canonical paid/grace expiry, finite and never later. Current entitlement expiry is `min(canonical expiry, grant.ValidUntil)` for mobile-grant authority; revoke/inactive state denies immediately. Notifications/refresh may shorten/revoke but cannot extend a mobile grant or enroll a new key. To renew a grant, the app automatically submits current verified local evidence again; no button/login required. Historical expired/revoked evidence may create/update a non-active grant/history link with past `ValidUntil`; it yields history/status, zero paid AI, and shared accounting identity. Existing owner-authorized installations use canonical owner entitlement rather than grant expiry.

No JWS age window is represented as owner proof. `LastEvidenceHash=SHA256(UTF8(jwsTransaction) || 0x1F || UTF8(jwsAppTransaction) || 0x1F || ASCII(canonical device ID))` is audit/idempotency metadata, not a bearer token and not a global one-use ban (legitimate retries reuse Apple evidence). Each HTTP retry needs a new challenge/assertion. Store no raw device ID or JWS in routine logs.

**Residual threat:** an attacker with the complete accepted Apple transaction, matching app transaction and device-ID material plus a valid new installation key may satisfy these checks. App Attest does not attest that submitted StoreKit device ID belongs to its key. This contract blocks raw UUID/token inheritance and a copied purchase JWS alone; it does not prove full-envelope replay/relay impossible. A copied complete envelope can at most obtain bounded mobile access and consume the same purchase allowance/aggregate guest/global budget; it cannot change owner, claim desktop, read account/other-installation content, or escape expiry/revocation. Shared quota depletion is a residual denial-of-service risk. Report that limit explicitly; do not invert B2 tests to hide it.

## 5. Resolution, errors and first desktop recovery (Task 2B / 3B)

`AnonymousPurchaseService.GetPurchaseContextAsync(string keyId, string productId, CancellationToken ct): Task<IapService.IapResult>`; `VerifyOwnerPurchaseAsync(string keyId, IapVerifyRequest request, CancellationToken ct): Task<IapService.IapResult>`; `RestoreMobileAsync(string keyId, IapRestoreRequest request, CancellationToken ct): Task<IapService.IapResult>`. Keep `IapService` public methods as delegating compatibility entry points. `MobilePurchaseAccessResolver.ResolveAsync(string keyId, CancellationToken ct): Task<MobilePurchaseAccess?>` returns `DeviceId`, `InstallationOwnerId`, nullable selected `PurchaseOwnerId`, nullable `Subscription`, `Authority`, nullable `GrantValidUntil`, and canonical `Entitlement`. All IDs are server resolved.

Device resolution first evaluates its owner-bound purchases and mobile grants, ranks as Task 4, and aggregates sticky paid history across applicable linked evidence. A supplied valid Owl session may provide account entitlement when no active independently proven mobile entitlement exists. An unrelated Owl session must neither replace active mobile rights nor acquire their quota/account-data authority. `DeviceContext.AccountId` is populated only for the actually selected account source or a verified session for that purchase's existing linked account; never infer it from a purchase link when logged out. Remove `account_required` projection for independently proven mobile rights. A legacy device without new proof may not inherit a linked purchase from its old UUID.

| HTTP/code | Required client behavior |
|---|---|
| 400 `invalid_purchase_request` / `invalid_transaction` | Stop malformed/unverified evidence; preserve transaction and saved text; no purchase retry loop. |
| 401 `invalid_device` / invalid account session | Resume existing App Attest key; rotate only if key actually invalid. Owl session recovery applies only to account operations. |
| 403 `invalid_device_proof` | Obtain a new challenge/assertion. No owner/paid mutation occurred. |
| 403 `purchase_owner_proof_required` | Use local verified Apple envelope on restore; never ask for Owl login to regain mobile access. |
| 403 `restore_evidence_mismatch` / `restore_evidence_unavailable` | Explicit Restore may refresh StoreKit. If it still fails, show restore failure and existing support route; never suggest paying again. |
| 403 `desktop_owner_proof_required` | Mobile remains usable. Show: “Your iPhone subscription is restored. To connect Windows, use the iPhone where you originally connected this purchase, sign in to the Owl account already linked to it, or contact support.” Only expose real existing contact UI; no invented mailbox. No backend support override is implemented by this contract. |
| 409 `subscription_already_linked` | Keep current mobile grant; account claim denied, no foreign account details. Deleted-account tombstone does not reopen. |
| 409 `subscription_already_active` | Refresh mobile access; do not call StoreKit purchase again. |
| 402 `subscription_inactive` | Claim/AI/new-content denied; retained paid read/review/delete/export stay under D3. Restore itself may return 200 with inactive status. |
| 429 `ai_quota_exceeded` | Task 6 actual limiting-window `Retry-After`, no provider attempt. |
| 503 `apple_unavailable` / `apple_identity_mismatch` | Retry later/Restore; do not change known paid history or extend paid authority. |
| 503 `subscription_reconciliation_required` | Existing Task 4 quarantine contract: persistent recovery/support guidance, no automatic retry loop, repurchase or data loss. |

Exceptional first-desktop recovery is deliberately unsolved after total original-key loss and no prior account claim: support must establish separate prior-owner evidence outside this release's automatic endpoint. Showing a support button is not evidence this operational process exists. Validate that route/process before claiming complete desktop recovery; it never gates ordinary mobile restore.

## 6. Current Apple primary references

Checked 2026-09-28; these establish API semantics, not a cryptographic server binding between Apple Account and a new App Attest key.

- [Current entitlements](https://developer.apple.com/documentation/storekit/transaction/currententitlements): active/grace entries exclude refunded/revoked purchases. [Transaction](https://developer.apple.com/documentation/storekit/transaction): StoreKit exposes signed current and historical transactions.
- [AppTransaction.shared](https://developer.apple.com/documentation/storekit/apptransaction/shared) supplies verified app evidence; [refresh](https://developer.apple.com/documentation/storekit/apptransaction/refresh()) may prompt and belongs to explicit user action. [AppStore.sync](https://developer.apple.com/documentation/storekit/appstore/sync()) is the explicit restore synchronization API.
- [Device verification algorithm](https://developer.apple.com/documentation/storekit/appstore/deviceverificationid), [transaction deviceVerification](https://developer.apple.com/documentation/storekit/transaction/deviceverification), and [VerificationResult](https://developer.apple.com/documentation/storekit/verificationresult) document the local fields and JWS forwarding.
- [appTransactionID](https://developer.apple.com/documentation/storekit/apptransaction/apptransactionid) is stable for an Apple Account/app and distinct per family member. [WWDC25 StoreKit](https://developer.apple.com/videos/play/wwdc2025/241/) says it is back-deployed to iOS 15; the symbol is annotated `@backDeployed(before: iOS 18.4, ...)`. Build with the current SDK, retain iOS 17 target, and test payload presence instead of imposing an iOS 18.4-only restore requirement.
- [AppTransaction payload](https://developer.apple.com/documentation/appstoreserverapi/jwsapptransactiondecodedpayload), Apple's [model](https://github.com/apple/app-store-server-library-python/blob/main/appstoreserverlibrary/models/AppTransaction.py) and [verifier](https://github.com/apple/app-store-server-library-python/blob/main/appstoreserverlibrary/signed_data_verifier.py) establish `receiptType`, `receiptCreationDate`, production `appAppleId` check and local device fields. Do not decode an unsigned `jsonRepresentation` as proof.
- [appAccountToken](https://developer.apple.com/documentation/appstoreserverapi/appaccounttoken) is developer correlation, not a password; [WWDC25 server APIs](https://developer.apple.com/videos/play/wwdc2025/249/) describes missing Family Sharing tokens. [App Attest validation](https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server) supplies app/key integrity and counters, not Apple Account authentication.

Task 2B sections 1–6 and its brief are frozen for implementer handoff. Task 3B and Task 6 briefs specialize client lifecycle and accounting/content integration without changing these wire names or authority boundaries.
