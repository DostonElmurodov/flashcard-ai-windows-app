## Lifecycle and ordering rules

1. On startup/foreground access refresh, register/resume a valid installation, enumerate current verified entitlements automatically, and submit owner verify when its server context is known; `purchase_owner_proof_required` goes to `/restore` with full evidence. Never invoke AppStore.sync/AppTransaction.refresh solely because the app launched. AppTransaction.shared failure is a failed check, not an absent purchase.
2. Explicit Restore invokes `AppStore.sync()` once. Retry AppTransaction.shared; only this explicit user action may call AppTransaction.refresh if shared is missing/unverified. Enumerate current evidence and restore it. Apple cancellation is a normal cancelled operation. No current subscription is distinct from network/signature/backend failure.
3. Current entitlements omit expired/revoked subscriptions. After an empty active scan, query `Transaction.latest(for:)` for the two existing allowed product IDs (monthly/yearly), verify locally and submit historical evidence with the same app/device envelope. Deduplicate by original transaction ID; no unbounded history crawl. Server 200 inactive status preserves WasEverPaid and accounting linkage. Empty discovery must not erase backend-known or already-confirmed local paid history; outage never means free. Historical evidence restores retained paid read/review only, never AI/add/edit authority.
4. Before a new purchase, capture installation key ID, app/entitlement authority revision and server token. No mandatory account refresh/login gate. If current independent mobile subscription already exists, refresh it rather than repurchase. Current Owl account is never an implicit destination owner. Pending/cancelled purchase sets no entitlement.
5. Process `Transaction.updates`, unfinished verified transactions and purchase/restore results through the same backend processor. Finish only after the server durably acknowledges that transaction's owner/grant/history result. A server timeout leaves it unfinished for StoreKit retry; do not buy again. A superseded UI request may still finish a durably acknowledged transaction, but must not persist stale token/entitlement/error. Installation-key change requires new proof/full mobile restore, never forwarding a prior owner's context under the new key.
6. Separate durable processing outcome from UI application: `PurchaseProcessingOutcome { backendAcknowledged: Bool, appliedToCurrentSession: Bool }`. Every mutation and every catch block checks the same captured operation/authority generation before changing errorText, token, isBusy or entitlement. Older failed verification cannot overwrite newer success (Task 8 O1). Account claim additionally captures destination account/session generation; completion after account switch cannot apply to the new account.
7. Valid key plus expired/lost JWT calls `/app-attest/resume` with a fresh assertion. Do not clearAll on ordinary network, backend timeout or out-of-order assertion denial. A genuinely invalidated App Attest key creates a new server installation and automatically attempts normal Apple restore. Each rejected proof retry uses a new challenge/counter; limit automatic retries to one per operation, then expose retry UI.
8. `EntitlementStore` recognizes server `mobile_restore` as independent mobile authority. Linking or logging out of an Owl account clears private account scope only; the new mobile grant stays until finite expiry/revocation. Preserve accepted offline expiry/paid-history rules; cached local flags never authorize a provider call.
9. Account claim never calls the old “verify to establish UUID association” path. Use the signed transaction from the evidence source plus existing account/device proof, and display `desktop_owner_proof_required` separately while keeping mobile access. Existing linked-account login remains the ordinary Windows path. The user supplied the support contact during this preflight: **dostone2100@gmail.com**. A “Contact support” action opens `mailto:dostone2100@gmail.com`; if mail cannot open, show the copyable address. Do not automatically include receipts, transaction/account IDs, device IDs, assertions or keys, and do not send any message. A working contact action does not implement or prove an operational owner-recovery procedure.
