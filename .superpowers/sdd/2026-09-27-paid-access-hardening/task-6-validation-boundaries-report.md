## Bounded carryover and risks

- **Reachable free excess-row gap:** `TestModeRouteTests` demonstrates that Development TestMode can create 12 active device rows and later turn off. For an ordinary unclaimed device with no subscription, resolution then becomes `free`. `DeviceWordService.UpsertAsync` checks the 10-row count only for absent/inactive rows, so an existing active 11th/12th row can still receive changed content under free. A premium/history import may also create excess active rows before a later free classification. The iPhone's `WordRepository.requireEditPermission` ranks local words by `(created_at, id)`, while the server's `DeviceWordEntity.CreatedAt` and generated `Id` are independent values and the upsert DTO carries no authoritative order. Applying server-created order here could reject a client-eligible word and allow a client-locked one. This remains an explicit owner/ordering integration item for the later phase; do not mistake this bounded change for complete free-row authorization. Exact acknowledgments and deletion should remain possible for excess retained rows.
- The stable anonymous owner, shared account/device quota, Retry-After timing, and numeric D2 policy were untouched. The B1/B2 failures and B4 skip are whole-feature blockers, not accepted final behavior. AccountSync storage/review/deletion behavior was not redesigned or given a 10-record cap.
- Multipart validation checks supported image signatures, not full image decoding; this matches the existing provider-entry validation contract. The unchanged service still validates direct calls. No live purchases, email, production database, deployment, remote workflow, or push occurred.
