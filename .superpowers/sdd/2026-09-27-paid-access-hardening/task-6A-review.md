# Task 6A independent scoped review

**Result: changes requested.** The uncommitted implementation has two blocking migration/readiness findings. This is a scoped review of Task 6A, not acceptance of Task 6B or a release decision.

## Findings

1. **P1 — Historical `legacy_unproven` purchase usage is silently classified as free.** In `test-results/paid-access-hardening/backend/src/Mavrylo.Data/Migrations/20260929150632_AddStableOperationUsage.cs:238-265`, a keyed `ai_usage` row goes to `free:<Device.Id>` whenever the device owner's count of `server_token` bindings is zero. The previous `AddAnonymousPurchaseRestore` migration deliberately places historical purchases under separate `legacy_unproven` owners, and such purchases need not have a `mobile_purchase_grant`. For a device with one historical legacy purchase, one valid keyed usage row, and no grant, the new migration therefore imports the row to the free bucket, inserts no reconciliation issue, and can set `Ready=true` at line 283. A later verified restore selects a purchase scope with none of that usage. The old UUID cannot establish whether the row belongs to that purchase, so the migration must retain an unresolved provenance item rather than treat the row as proven free. Add a populated migration fixture with this exact case and assert the original row remains, the issue inventory identifies it, and admissions stay closed. Preserve a genuinely free device positive control.

2. **P1 — Existing paid mobile purchases can be marked ready with zero observed usage.** The pre-Task-6A device filter reserved `ai_usage` only when `isFree`; anonymous trial/premium/grace requests were not recorded there (`Filters/AiProtectionFilter.cs` in HEAD `3957f3e`, prior lines 177-185). The new migration creates purchase scopes at `AddStableOperationUsage.cs:211-227`, but its issue inventory at lines 254-269 covers invalid/unmapped legacy rows, mobile grants, and deleted-account tombstones only. An existing, unclaimed `server_token` purchase with no grant and no `ai_usage` thus receives a zero bucket and `Ready=true`, although absence of rows cannot prove that it had no paid AI operations. The brief expressly requires unresolved historical purchase consumption to remain visible and fail closed before cutover. Add a populated migration fixture for an existing server-token purchase with zero legacy rows; assert an issue is retained and readiness is false. A genuinely new or genuinely free empty installation should remain a passing positive control. The production reconciliation decision is separate; this finding concerns local migration classification.
