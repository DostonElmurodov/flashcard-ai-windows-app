## Current behavior in source

Backend exact saved identity now uses `(DeviceUuid, ClientWordId)` with PostgreSQL C collation and a unique non-null-ID index. Semantic text/language uniqueness is removed; an explicit ID never falls back to another saved ID. The additive migration preserves legacy payloads and leaves missing creation time unknown. It raises `device_word_client_id_conflict` before index creation if historical duplicate IDs exist. Local and server ordering use finite SQLite REAL / PostgreSQL double values followed by SQLite BINARY / PostgreSQL C UTF-8 ID order, including composed/decomposed Unicode and BMP/non-BMP ties.

Device order GET/POST use the existing device library/proof, at most 500 entries and a 256,000-byte POST cap. The server keeps a per-library revision under the existing mutation lock, rejects stale or conflicting metadata, accepts exact retries without mutation, preserves omitted rows and payloads, and reports a complete first-ten set only when every active row has exact ID/time metadata. Unknown IDs create metadata-only retained rows. Upsert, delete, reservation, and AI checks use exact identity; existing true-free content changes above ten require complete order and a first-ten ID. Ordinary new additions at the cap return 402 before ordering, and out-of-ten AI is denied before provider. ID-less ambiguous saved/reservation matches are denied rather than chosen arbitrarily. The pending policy question is whether an unknown metadata-only ID *inside* the first ten may later receive content when the retained library already exceeds ten; this source path is not considered accepted until that answer is applied.

The iOS checkpoint sends exact SQLite `created_at` REAL on device upsert. Its newer, **unverified** source reads current local rows in `ORDER BY created_at,id`, fetches server revision, posts bounded metadata batches, retries a 409 at most twice after regenerating from current local IDs, and matches eligible IDs by UTF-8 bytes. It checks the queued local content before sending and before acknowledging a late response. Deletes now queue one exact server deletion per removed saved ID and clear only that ID's sync acknowledgment. The subsequent **unexecuted** AI source block rejects duplicate app-owned saved matches before choosing an ID for word-detail AI, reconciles complete server order before uncached primary word-detail and secondary review AI, and passes exact IDs on the wire. Secondary cached content bypasses order and provider calls; ID-specific cache keys keep canonically equivalent but byte-distinct IDs separate. Historical text-only secondary cache entries without proven saved-ID ownership cannot safely authorize a different saved ID, so ID-specific requests use a new cache key. AccountSync storage, versions/cursors/tombstones, review data, and pending payload architecture were not modified.
