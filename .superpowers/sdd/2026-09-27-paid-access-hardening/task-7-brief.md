## Задача 7. Защита расходов непосредственно у AI-провайдеров

**Файлы:** B `OpenAiJsonService.cs`, `GeminiJsonService.cs`, `FallbackAiJsonService.cs`, DI в `Program.cs`, `appsettings.example.json`, `ops/linux/owl-api.env.example`; создать `AiSpendGuard.cs`, `AiSpendReservationEntity.cs`, миграцию, `tests/AiSpendGuardTests.cs`; расширить `AiProviderServiceTests.cs` и `FallbackAiJsonServiceTests.cs`.

**Interfaces:** `TryReserveAsync(AiAttempt attempt, CancellationToken ct): Task<SpendReservation?>`, `CompleteAsync(Guid reservationId, AiAttemptUsage? usage, CancellationToken ct): Task`. `AiAttempt` содержит субъект, operation, provider/model, серверный attempt ID, верхнюю оценку затрат; резерв хранит integer micro-USD. `AiAttemptUsage` содержит фактически полученные input/output/reasoning/cache usage, а отсутствие usage не означает нулевой расход. Вызовы выполняются из provider-адаптера перед HTTP, а не только из одного контроллера.

- [ ] На fake-провайдерах задать бюджет 100 условных единиц: резервы 60 и 60 не проходят одновременно; при резерве 60 затем 40 лимит достигнут и следующий HTTP-вызов отсутствует. Реальных цен эти числа не задают.
- [ ] Добавить атомарные пределы по global, guest и account, а также серверный выключатель новых AI-вызовов. `test_mode=true` может обходить коммерческую политику в тестовом контуре, но **не** общий предел реальных расходов.
- [ ] Ограничить вход, изображения, выходные токены, параллельность и длительность. Для каждого поддерживаемого provider/model/operation обязательны положительные пределы и проверяемая верхняя оценка цены. Неизвестный model/price/input-cost profile запрещает запрос; тарифы и единицы проверяются по документации провайдера при реализации. Если верхнюю оценку расхода доказать нельзя, не называть расчёт жёстким денежным пределом и не включать такой путь в release.
- [ ] Резервировать первичный вызов и fallback отдельно; запретить fallback после отказа авторизации/квоты/бюджета/отмены. Учесть скрытые HTTP-retry: каждый реальный оплачиваемый повтор либо зарезервирован отдельно, либо retry отключён.
- [ ] При timeout/crash/неизвестном результате сохранять консервативный резерв; не возвращать его автоматически по TTL. Освобождать только доказанно неотправленный запрос или подтверждённую разницу с actual usage; завершение идемпотентно. Отмена клиента после отправки не отменяет возможный счёт провайдера.
- [ ] Метрики: операции allowed/denied, provider attempts, reservations, usage, fallback, лимиты. Без JWT/JWS, личных текстов карточек и секретов в журналах. Сигнал предупреждения при 80%, отказ нового расхода при 100%; это внутренние события, не автоматическая отправка сообщений из этой задачи.
- [ ] Проверки response JSON caps для обоих провайдеров, oversized image/text, невалидного JSON ответа, cache hit без нового HTTP, двух реплик и рестарта; коммит.

**Готово:** разрешённая подписка или баг клиентского лимита сами по себе не дают неограниченный расход. Предел действует на все контролируемые этим backend provider-вызовы; другие сервисы с теми же ключами должны быть учтены отдельно. Бюджет интерфейса провайдера не считать hard cap без проверки его реального поведения.

## Controller HTTP/pricing preflight
Read provider-guard-preflight.md in this SDD directory before implementation; it records current call paths and official provider/.NET sources, not approved production budget values. Concrete HTTP pitfalls: existing default completion buffers before parser checks; streaming requires both an incremental cap and a deadline that covers the body; default redirects are enabled and Gemini uses a custom API-key header. Disable automatic provider redirects/retries or separately reserve/prove every actual permitted attempt. Named/new HTTP clients must still be exercised by fake tests. Test oversized unknown/chunked response length and headers-first/body-timeout cases. These are part of the already requested response caps/attempt accounting, not optional unrelated HTTP cleanup.


## Fallback status preflight
The current provider fallback positive tests use provider500 failures; these should remain valid within separate successful reservations. No current test establishes intentional fallback after provider401/403/429. Add explicit no-fallback/no-alert controls for application authorization/quota/spend denials and client cancellation, and decide/test provider authorization/quota statuses consistently with the plan's no-fallback requirement. Preserve conservative submitted reservations on non-success responses: an HTTP error alone is not proof of zero cost. Final accounting must not add reasoning/thinking tokens twice if the provider already includes them in billed output totals; missing, negative, inconsistent, oversized or unknown-model usage cannot release a reservation as if it were zero. Unknown pricing/subject/config and checked integer arithmetic overflow must produce a controlled no-provider-call denial, not a fallback attempt or500. These are implementation checks, not approved production prices or budget values.
