# Apple validation preflight — Task 4, read-only

Current backend `AppleJws` pins Apple Root G3, builds X509 chain at current time with revocation disabled, requires ES256, and verifies JWS signature. It does not inspect the Apple signing-purpose OIDs. This is not evidence that an attacker can forge Apple receipts.

Checked the current [official Apple Node verifier](https://github.com/apple/app-store-server-library-node/blob/main/jws_verification.ts): it requires leaf purpose OID `1.2.840.113635.100.6.11.1`, intermediate purpose OID `1.2.840.113635.100.6.2.1`, and certificate validity checks. Its online-check mode uses current time and OCSP; offline mode uses the signed payload date. Verification failure and retryable network/revocation-check failures are distinguished. Compare actual semantics and test positive legitimate chains before introducing changes; do not simply enable an OS revocation flag and declare equivalence.

Reference-library version matters: Apple's [Python advisory](https://github.com/apple/app-store-server-library-python/security/advisories/GHSA-8f6j-263m-g72x) reports stale OCSP responses accepted by versions through 3.1.1, fixed in 3.1.2. If differential tests use Python, pin a patched version. The application is .NET and is not reported as using that Python package.

Task 4 should preserve the safe Task1 controls: matching canonical active state can supersede historical refund semantics; unrelated canonical original ID must be rejected without updating another purchase. Production must reject persisted Sandbox/LocalTesting and incomplete subscription data, while an explicitly isolated Sandbox server remains usable. Existing ownership/claim markers must survive status refreshes.

No certificate, receipt or live-data mutation was performed. Actual Apple signing-chain vectors and physical-device acceptance remain work to do, not established by this comparison.

Official fixture discovery for the implementer: Apple's Node repository has tests/unit-tests/jws_verification.test.ts, tests/resources/certs/testCA.der, and tests/resources/mock_signed_data/. tests/util.ts constructs SignedDataVerifier with that test root and offline checks. These are reference test certificates, not proof of a live Apple purchase. If incorporating fixtures, pin an upstream commit, retain MIT attribution, and keep test trust-root injection inaccessible to runtime configuration. The production trust root must remain pinned to Apple. Source: https://github.com/apple/app-store-server-library-node/tree/main/tests .
The official jws_verification.test.ts also embeds positive real-Apple chain constants and synthetic valid/invalid leaf/intermediate-purpose OID vectors; chain tests use a fixed effective date (October 2025). Mock signed payloads include valid notification, renewal and transaction plus wrong bundle/missing x5c. These let Task4 test purpose checks positively and negatively, and distinguish historical signing-time validity from current certificate expiry.
