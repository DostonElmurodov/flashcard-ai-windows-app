### [P2] Select the latest historical transaction before deduplicating a subscription chain

Location: `D:/07 Hobby/FlashcardAI/test-results/paid-access-hardening/ios/Infrastructure/Purchases/StoreKitPurchaseEvidenceSource.swift:108` (surrounding selection at lines 98–109).

`latestHistoricalEvidence` visits product IDs in caller order and keeps the first transaction for each original transaction ID. `StoreKitService` supplies monthly before yearly. If a customer upgraded monthly to yearly in the same subscription chain, then the yearly subscription expired or was revoked, current entitlements can be empty while `Transaction.latest(for:)` returns an older monthly transaction and the newer yearly transaction. This code keeps monthly and discards yearly without comparing recency or upgrade state. When all transactions have already been finished, the unfinished scan cannot recover the dropped evidence.

The backend appropriately requires the local proof's product to match the same original ID's canonical Apple product (`AnonymousPurchaseService.cs:113–116`). The obsolete monthly proof therefore receives `503 apple_identity_mismatch`. On a new installation without independently retained paid history, the canonical expired-paid proof never reaches restore, so the app cannot establish the paid-history link needed to retain full expired-paid review access. On an existing installation it can leave a persistent restore error. This is a restoration/history regression, not unauthorized paid access or a reason to weaken server proof checks.

Fix the live evidence selection through a testable selector/enumeration seam so configured product order cannot discard the newest appropriate verified transaction in a chain. Add a monthly-to-yearly expired-chain regression with no current or unfinished transactions, exercise both product orders, and assert the canonical evidence reaches the backend and paid history applies. A fake evidence source that directly supplies the already-selected result does not test this bug. Simply returning every historical candidate is insufficient: the service's restoration loop retains `firstFailure` from an obsolete earlier candidate even if a later canonical candidate succeeds, so explicit restore still returns false and leaves an error. Either select correctly before processing, or explicitly resolve only the obsolete same-chain mismatch after canonical acknowledgment, without hiding unrelated failures.

Evidence classification: independently traced current source and corroborating existing same-original monthly/yearly fixtures (`AnonymousPurchaseRestoreTests.swift:253–281`); no physical StoreKit reproduction or new Mac execution was performed. Existing historical test at line 554 uses a fake source containing one preselected envelope and does not cover the live selector.
